# KartLink diagnostics and lifecycle checks

The original `eden-room.exe` buffered its stdout when started with pipes. With two lightweight emulator-room clients, no join or departure events arrived while that server was running; they appeared after normal process exit. The replacement uses the same server libraries and protocol, with unbuffered stdout/stderr in its standalone entry point. `tests/live-room-events.test.cjs` verifies both clients appear and leave while the server is still running across repeated sessions. It uses the existing local probe harness and does not launch a game or modify Playit.

Process shutdown now waits for the actual child exits, escalates after a deadline, and reports failures. Startup failure owns its process cleanup. Configuration read errors no longer bypass authorization cleanup. Tunnel creation persists a unique intent before the remote request and reconciles only an exact matching name, agent and UDP destination; uncertain outcomes do not blindly create a second tunnel. This recovery is covered by simulated Playit API tests, not by modifying a real Playit account.

The app now distinguishes a running local room, an allocated tunnel, and an external connection that has not been tested. Player data remains based on server log events, so it should not be treated as an authoritative protocol snapshot. The authentication window limits navigation to Playit domains, using the system browser as a fallback for outside sign-in providers; other provider flows still need hands-on validation.

The installed 1.0.2 app was measured with an isolated profile on a warm machine: the first window took 156–184 ms and the initial control was available in 245–275 ms across four runs under Playwright. This did not reproduce the reported 10–30-second delay, and debug instrumentation and warm caches limit the comparison. The startup path now creates the window before waiting for credential initialization and postpones the update check. `scripts/measure-startup.ps1` can record the actual process-to-window delay from the installed app when no KartLink process is running. A recent Windows Defender event reported submitting the room-server executable for analysis, but it does not establish the cause of the delay before the app window appears.

Validation: `npm test` passed 30 tests; `npm run test:integration` passed three real-process tests; `npm run test:ui` passed eight Electron UI tests; `npx tsc --noEmit` passed. `node tests/package-smoke.cjs` launched the 1.0.3 unpacked and extracted portable builds with isolated profiles and verified version and zoom. `npm run package` built both distributions. The installer was built but not installed over the active app; the public Playit path was not retested. The standalone server source is provided in `release-build/kartlink-eden-room-source.zip`.
